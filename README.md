# OSM 洪水分析水域面 API

按 OSM 关系号提交**逐次递增修订**的完整节点经纬度与无序 way（含 `outer` /
`inner` 角色），服务按节点引用拼接 way（允许线段反向），生成一个外环、至多
一个内环的 GeoJSON Polygon，并管理"当前供数面"的状态机。

每次上传还会与提交前的供数面比较，把**水域覆盖发生正面积变化的 1° 经纬格**
记为一个变更组，供下游洪泛栅格缓存按游标增量读取、只重算确实变化的格子。

技术栈：**FastAPI + Shapely + SQLite（WAL 模式）**，可 `docker compose` 启动。

## 快速启动

```bash
docker compose up --build
# 打开交互文档（可直接上传、取面、读变更流）
open http://localhost:8000/docs
```

本地无 Docker 时：

```bash
pip install -r requirements.txt
FLOOD_DB_PATH=./flood.db uvicorn app.main:app --reload
```

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/relations/{relation_id}/revisions` | 上传一个完整修订（修订号必须严格递增） |
| GET  | `/relations/{relation_id}/revisions/{revision}` | 按修订号读取**原始输入 + 几何 + 状态** |
| GET  | `/relations/{relation_id}/revisions` | 列出该关系全部修订号与状态 |
| GET  | `/relations/{relation_id}/current` | 取当前供数面（最新有效修订） |
| GET  | `/changes?after=&limit=` | 按游标读取修订变更流（1° 格重算清单） |
| GET  | `/health` | 健康检查 |

### 上传请求体

```json
{
  "revision": 1,
  "nodes": [
    {"id": 1, "lat": 0.0, "lon": 0.0},
    {"id": 2, "lat": 0.0, "lon": 1.0},
    {"id": 3, "lat": 1.0, "lon": 1.0},
    {"id": 4, "lat": 1.0, "lon": 0.0}
  ],
  "ways": [
    {"id": 10, "role": "outer", "node_refs": [1, 2, 3, 4, 1]}
  ]
}
```

约束：每次提交为该修订的**完整快照**；最多 **8 条 way、32 个节点**；way
无序，拼接时可反向遍历；`node_refs` 闭合方式沿用 OSM 惯例（首尾节点相同）。

## 修订变更流（下游栅格缓存重算）

下游洪泛栅格缓存按 **1°×1° 经纬格**组织，格号取格西南角的整数经纬度：
格 `(lon, lat)` 覆盖 `[lon, lon+1) × [lat, lat+1)`。

每次**被接受的**上传在提交修订的**同一事务**内生成一个变更组：比较提交前
后的当前供数面，记录覆盖发生**正面积变化**的格子，连同关系号、修订号一起
落库。`GET /changes` 按游标读取：

```bash
curl 'http://localhost:8000/changes?after=0&limit=100'
```

```json
{
  "groups": [
    {
      "group_id": 1,
      "relation_id": 42,
      "revision": 1,
      "cells": [{"lon": 0, "lat": 0}],
      "created_at": "2026-11-18T09:30:00.000Z"
    }
  ],
  "next_cursor": 1
}
```

用 `after=<next_cursor>` 轮询即可持续增量消费；返回空页时 `next_cursor`
保持不变。

### 覆盖与变化的判定

- 面与格的交集**面积大于零**才算覆盖该格：**内环（洞）不算覆盖**，**仅沿
  格边接触**（共享边界、面积为零）也不算覆盖。
- 变化格取自前后两个供数面的**对称差**：新覆盖、不再覆盖、以及格内覆盖
  面积发生增减的格子都会被记录。
- way 顺序/方向变化但面未变时，变更组照常生成但 `cells` 为空，**不产生
  重算格**。
- 无效修订会**撤下旧供数面**：旧面覆盖的格子记入该次变更组；**连续无效
  不重复撤下**（后续无效修订的组为空）；恢复有效修订时再次记录新面的
  格子。

### 变更组的一致性保证

- 每个被接受的修订**恰好一个**变更组，二者**同事务提交**：存储失败整体
  回滚，不会留下半份修订或半组记录；被拒绝的上传（修订号冲突、输入校验
  失败）不落库也不产生组。
- `group_id` 单调递增且**连续无空洞**（写事务串行提交，回滚不消耗序号），
  读者按 `group_id` 顺序消费，并发读取、失败回滚或进程重启后都**不会漏
  组、拆组**，也不会出现与供数状态不符的记录。

## 校验与状态机

以下情况修订标记为 `invalid`，**原始输入完整保留**，响应中返回错误码及相关
way id，当前面**停止供数**（`/current` 返回 409）：

- `missing_nodes`：way 引用了未提交的节点
- `broken_ring`：单 way 未闭合、way 间断环、外环拆成多个连通分量
- `fork`：三条以上 way 端点汇聚，或 way 端点落在另一条 way 内部（T 型分叉）
- `self_intersection`：环自交 / 节点重复访问（8 字形等）
- `inner_ring_violation`：内环触碰外环边界、越过外环或位于外环之外
- `missing_outer`：没有 `outer` 角色的 way

停止供数期间，**上一个有效面仍可按修订号读取**，响应里的
`last_valid_revision` 指向它；后续出现有效修订后 `/current` 自动恢复供数。

输入约束违例（超 8/32 上限、角色非法、修订号非递增等）返回 422 / 409，
**不落库**。

## 一致性、原子性与持久化

- SQLite 启用 **WAL + `synchronous=FULL`**：提交即 fsync，重启后数据可查；
  读不阻塞写，读者只能看到完整提交的修订与变更组。
- 每次写入在单个 `BEGIN IMMEDIATE` 事务内完成"递增检查 + 覆盖差分 + 修订
  与变更组插入"，进程与进程间均由 SQLite 写锁串行化；存储失败整体回滚，
  **不会留下半份修订或半组变更**。
- 覆盖差分在写事务内针对"提交时刻的最新前一修订"计算，因此并发上传时记
  录的变化序列必然与实际提交的供数状态序列一致。
- 原始输入、几何、状态、变更组同事务写入，因此并发上传与读取看到的同一
  修订四者必然一致。
- 数据库位于挂载卷 `/data/flood.db`（环境变量 `FLOOD_DB_PATH` 可改）。
